CHESS TRACKER SYSTEM DESCRIPTION
================================

Purpose of this file
--------------------
This file is a detailed technical description of the full system.
It is written so that another AI or a human can understand:

- what the project does
- what the major modules are
- in what order the data moves through the system
- how the vision pipeline works
- how the internal chess state is updated
- how the backend and frontend fit onto the same data flow
- what assumptions and limitations currently exist

The frontend is included only as much as needed to explain the whole system.
The main focus is:

- vision
- chess logic
- backend state handling
- end-to-end data flow


1. High-level goal of the system
--------------------------------
The final goal of the project is to observe a real physical chessboard through a camera
and keep a synchronized digital game state from it.

The system is intended to do the following:

1. Read a live video stream from a camera.
2. Detect the physical chessboard in the image.
3. Warp the board into a more regular top-down view.
4. Split the board into 64 square images.
5. Classify each square into one of 3 categories:
   - empty
   - white piece present
   - black piece present
6. Build an 8x8 occupancy representation from those square classifications.
7. Stabilize noisy observations over time.
8. Compare the new stabilized board occupancy with the previous accepted board occupancy.
9. Infer which legal chess move explains the observed change.
10. Apply that move to the internal chess state.
11. Send the updated game state to the backend.
12. Let the backend publish the new state to the frontend.
13. Let the backend also run Stockfish analysis in the background.
14. Later, a robot arm can use the best engine move payload from the backend.


2. Major system parts
---------------------
The project can be seen as 4 main layers:

1. Vision layer
   Files under `vision/`
   Responsible for image processing and move observation.

2. Chess logic layer
   Files under `chess_logic/`
   Responsible for legal chess interpretation and internal board state.

3. Backend layer
   Files under `backend/`
   Responsible for API, WebSocket state broadcasting, engine analysis.

4. Frontend layer
   Files under `frontend/`
   Responsible for board rendering and showing analysis data to the user.


3. Main entrypoints
-------------------
There are 2 main runtime entrypoints in practice:

1. Vision live runner
   `vision/app/run_live.py`

   This is the camera-based live pipeline.
   It opens the camera, runs the tracker, and optionally syncs accepted moves to the backend.

2. Backend app
   `backend/main.py`

   This creates the FastAPI application.
   It keeps the authoritative backend-side state and exposes HTTP and WebSocket endpoints.

In normal operation:

- the vision live runner observes the real board
- the backend stores and serves the digital game state
- the frontend subscribes to backend state changes


4. End-to-end data flow
-----------------------
The easiest way to understand the system is to follow one move from the camera all the way
to the frontend.

4.1 Camera frame acquisition
----------------------------
File:
`vision/app/run_live.py`

Class:
`LatestFrameCamera`

What it does:

- opens the selected camera
- starts a background thread
- continuously reads frames
- always stores the newest frame and sequence number

Important detail:

- the code does not process every captured frame
- it always keeps the latest frame
- the processing thread reads the newest available frame when it is time to process

This reduces lag because the system does not get stuck processing an old backlog of frames.


4.2 Live processing loop
------------------------
File:
`vision/app/run_live.py`

Class:
`LiveProcessor`

What it does:

- owns one `ChessVisionTracker`
- owns optional backend sync client
- runs a worker thread
- decides when to process the next frame

The processing cadence is controlled by:

- `process_every_nth_captured_frame`

This means the camera may capture at 30 FPS, but the tracker may only process every 6th frame.

This is an intentional speed/latency tradeoff.


4.3 One processed frame enters the tracker
------------------------------------------
File:
`vision/pipeline/tracker.py`

Class:
`ChessVisionTracker`

This class is the core of the vision system.
It owns:

- the current vision-side game state
- the stabilizer
- the occupancy classification model
- board detection state
- the current accepted occupancy
- previous frame caches for partial reclassification
- initialization buffers

The tracker has two major modes:

1. initialization mode
2. tracking mode

The tracker starts in initialization mode.


5. Initialization phase
-----------------------
The initialization phase is important because the system must first align the camera image,
understand the board orientation used by the current setup, and verify that the observed
board looks like the expected starting chess position.

5.1 Board detection
-------------------
Files:
- `vision/pipeline/tracker.py`
- `vision/pipeline/board_detector.py`
- `vision/board/find_chessboard.py`
- `vision/board/squares.py`

Step-by-step:

1. The frame is converted to grayscale.
2. `detect_board_on_frame()` is called.
3. This tries to detect the board grid and calculate a homography matrix.
4. The homography matrix is used to create a warped board image.
5. The warped board is analyzed to estimate the square boundaries.
6. The result includes:
   - homography matrix
   - warped board data
   - square bounding boxes
   - square centers

Important conceptual point:

The homography is used to "flatten" the board perspective.
It does not by itself give a final chess-side orientation.
It only helps produce a normalized board image.


5.2 Square classification during init
-------------------------------------
Files:
- `vision/pipeline/tracker.py`
- `vision/pipeline/batch_classifier.py`
- `vision/models/occupancy_color_model.py`

What happens:

1. The warped board image is split into 64 square crops.
2. The PyTorch model classifies all 64 squares.
3. Each square is classified as:
   - 0 = empty
   - 1 = white piece
   - 2 = black piece

The output is:

- an 8x8 label grid
- an 8x8 confidence grid


5.3 Init buffering
------------------
The system does not trust just one frame during initialization.
Instead it stores multiple classified board observations.

Relevant config values:

- `init_buffer_frames`
- `init_sample_every`

What happens:

1. The tracker collects several init classification samples.
2. It may skip some frames according to `init_sample_every`.
3. After enough samples are collected, it performs a weighted vote.

Why this exists:

- one frame may be noisy
- a piece might be blurred
- lighting might temporarily be bad

The weighted vote helps produce a more reliable initial occupancy.


5.4 Orientation handling during init
------------------------------------
This is the most subtle part of the current system.

Current behavior:

- the code does not read a clean "rotation angle" directly from the homography
- instead it tests candidate grid orientations on the detected square-center layout
- after that, it applies an additional fixed transform to move the board into the system's
  internal standard orientation

Important practical consequence:

The current system is not fully orientation-agnostic.
It effectively assumes a preferred real-world setup.

In the current working setup:

- the camera is approximately above the board
- the white side should appear on the left side of the image
- the black side should appear on the right side of the image

If the board is physically reversed left-right, the initialization distance becomes large,
often around 32, and initialization is rejected.

This happens because the observed occupancy is compared against a fixed expected start occupancy.


5.5 Start position verification
-------------------------------
After init voting and orientation normalization, the tracker compares the observed board
to the expected chess starting position.

Relevant state:

- `expected_start_occ`

What it means:

- the tracker knows what the start position occupancy should look like
- it compares the observed occupancy to that expected occupancy
- if too many cells differ, initialization fails

Relevant config:

- `init_max_dist`

If the difference is greater than this threshold:

- board detection state is reset
- init buffers are cleared
- init restarts

This is why incorrect board orientation or heavy misclassification causes repeated init failure.


6. Tracking phase after init
---------------------------
Once initialization succeeds:

- the tracker stores an accepted baseline occupancy
- it stores the previous warped image
- it stores previous raw labels and confidences
- it sets `initialized = True`

From this point onward the tracker enters the normal live tracking loop.


7. Processing a frame in tracking mode
--------------------------------------
The main method is:

- `ChessVisionTracker.process_frame()`

The stages are:

1. Warp the current frame to board view.
2. Classify the board again.
3. Convert raw board view to the internal standard orientation.
4. Compare the new observation to the previous accepted board state.
5. Pass the new observation through the stabilizer.
6. If the stabilizer emits a stable new board, try to resolve it into a legal move.
7. If a legal move is consistently supported, apply it to the internal chess state.


8. Full classification vs partial classification
------------------------------------------------
Files:
- `vision/pipeline/tracker.py`
- `vision/pipeline/square_diff.py`
- `vision/pipeline/batch_classifier.py`

The tracker does not always reclassify all 64 squares from scratch.

There are 2 modes:

1. full classification
2. partial classification

Full classification:

- warp the board
- classify all 64 squares

Partial classification:

- compare the current warped board image to the previous warped board image
- estimate which squares changed the most
- reclassify only those squares
- keep the previous predictions for the unchanged squares

Why this exists:

- speed optimization
- most frames only change in a few places

Relevant config:

- `partial_reclassify`
- `partial_diff_threshold`
- `partial_max_squares`
- `full_reclassify_interval`

This means:

- the system can be fast most of the time
- but still periodically refresh the full board


9. Standardized occupancy representation
----------------------------------------
After classification, the tracker produces:

- `labels_std`
- `confs_std`

These are already converted into the system's internal standard board orientation.

That means:

- row/column indices now have a stable meaning inside the program
- chess logic can interpret them consistently

The occupancy representation only stores:

- empty
- white
- black

It does not identify the exact piece type visually.
The exact move is inferred by chess legality, not by direct visual piece-type recognition.


10. Stabilizer role
-------------------
File:
`chess_logic/stabilizer.py`

This layer is very important.
It is the boundary between noisy vision output and chess decision logic.

The stabilizer receives:

- occupancy grid
- confidence grid

Its job is:

- smooth out noisy classifications
- avoid reacting to one unstable frame
- emit only stable board states

The stabilizer does not know chess rules.
It only decides:

- whether the observed occupancy is stable enough
- whether a change should be emitted or held back

This is important architecturally:

- vision decides what the board looks like
- stabilizer decides whether that view is stable
- chess logic decides whether the stable change is a legal move


11. Comparing stable observation to accepted state
--------------------------------------------------
Once the stabilizer emits an occupancy:

1. the tracker converts it to `stable_occ`
2. it compares `stable_occ` to `accepted_occ`

If they are identical:

- no new move happened
- candidate move buffer is cleared
- result mode becomes `stable-same`

If they differ:

- the tracker tries to explain the change as a legal chess move


12. Legal move resolution
-------------------------
Files:
- `vision/pipeline/tracker.py`
- `chess_logic/game.py`
- `chess_logic/resolver.py`

This is a key design choice of the project:

The model does not try to visually classify exact chess pieces and moves directly.
Instead:

1. the model only says whether a square is empty/white/black
2. the chess logic checks which legal move could produce the new occupancy

This is a much more robust approach for physical chess tracking.

How resolution works:

1. The tracker calls `game.resolve_from_occupancy(...)`.
2. That calls `resolve_move_from_occupancy(...)` in the resolver.
3. The resolver iterates legal moves from the current board.
4. For each legal move it computes the expected occupancy after that move.
5. It compares that expected occupancy to what vision observed.

There are two matching modes:

1. exact match
2. fuzzy match


13. Exact and fuzzy resolution
------------------------------
Exact mode:

- if a legal move leads to exactly the same occupancy as observed, that move is accepted

Fuzzy mode:

- if exact match fails
- and confidence data is available
- the resolver can allow a small amount of occupancy mismatch

Relevant config:

- `fuzzy_max_noise_cells`
- `fuzzy_max_weighted_cost`

This helps when:

- one or two squares are misclassified
- the board is otherwise visually correct


14. Vote-based move acceptance
------------------------------
Even if a legal move is found, the tracker still does not immediately trust it.

It stores move candidates in:

- `candidate_move_buf`

Then it asks:

- which UCI move was most common recently?
- was it seen enough times?

Relevant config:

- `move_vote_window`
- `move_vote_min_count`

This creates a second layer of filtering:

- stabilizer filters visual occupancy noise
- vote buffer filters move-level noise


15. Applying the move to the internal chess state
-------------------------------------------------
If a candidate move passes voting:

1. the tracker calls `game.apply_uci(best_uci)`
2. the `Game` object checks legal move application
3. a `MoveRecord` is created
4. the internal board is updated
5. move history is extended
6. game result flags are updated if necessary

At this point:

- the move is officially accepted
- the tracker updates `accepted_occ`
- the move is ready to be sent to the backend


16. Chess logic layer
---------------------
Files:
- `chess_logic/game.py`
- `chess_logic/resolver.py`
- `chess_logic/types.py`
- `chess_logic/stabilizer.py`

This layer is the "meaning" layer of the system.

It does not look at raw images.
It only works with:

- board states
- occupancies
- legal chess rules

Main responsibilities:

1. store the authoritative internal board state
2. check legal moves
3. resolve occupancy changes into legal moves
4. build backend-facing state dictionaries
5. produce PGN export


17. Backend sync from vision
----------------------------
File:
`vision/app/run_live.py`

Class:
`BackendSyncClient`

What it does:

- when the vision tracker accepts a move
- it sends a POST request to backend `/api/move`
- the payload is the accepted UCI move

There is also:

- `/api/new-game`

This is called:

- at live start, if configured
- on manual tracker reset, if configured

This keeps the backend-side game synchronized with the tracker-side game.


18. Backend architecture
------------------------
Files:
- `backend/main.py`
- `backend/core/state.py`
- `backend/api/routes.py`
- `backend/services/ws_service.py`
- `backend/services/engine_service.py`

The backend has 3 major responsibilities:

1. store the backend-side game state
2. serve that state to clients
3. run engine analysis in the background


19. Backend startup sequence
----------------------------
File:
`backend/main.py`

Startup order:

1. FastAPI app is created.
2. CORS middleware is added.
3. WebSocketHub is created.
4. On startup event:
   - the current event loop is stored in the WebSocketHub
   - a `BackendState` object is created
   - the backend state gets a notifier callback that broadcasts state changes

This means:

- the backend state is not created at plain import time
- it is created when the app starts


20. BackendState responsibilities
---------------------------------
File:
`backend/core/state.py`

`BackendState` is the backend-side coordinator.

It owns:

- a `Game`
- an `EngineAnalysisService`
- an optional notifier callback

It is responsible for:

- `get_state()`
- `new_game()`
- `apply_uci()`
- scheduling engine analysis
- receiving analysis results
- exposing robot best-move payload

Important design point:

The backend keeps its own authoritative game state.
The vision runner does not directly mutate frontend state.
It only sends accepted moves to the backend.


21. Engine analysis flow
------------------------
Files:
- `backend/core/state.py`
- `backend/services/engine_service.py`

How Stockfish analysis works:

1. Backend state creates `EngineAnalysisService`.
2. That opens the Stockfish executable through python-chess.
3. A background worker thread waits for analysis tasks.
4. When game state changes, backend schedules analysis.
5. The worker analyzes the current position.
6. The result contains:
   - evaluation score
   - principal variation
   - SAN line
   - optional mate information
7. The backend stores those top lines if the position still matches the original snapshot.

This snapshot check is important.
It avoids writing stale engine results onto a newer position.


22. Backend API
---------------
File:
`backend/api/routes.py`

HTTP endpoints:

- `GET /api/health`
  Simple health check.

- `GET /api/state`
  Returns current full backend game state.

- `POST /api/new-game`
  Resets backend game state.

- `POST /api/move`
  Applies a UCI move to backend state.

- `GET /api/robot/best-move`
  Returns best move payload derived from engine top line.

WebSocket endpoint:

- `WS /api/ws/state`

This pushes state updates to connected frontend clients.


23. WebSocket state broadcasting
--------------------------------
File:
`backend/services/ws_service.py`

`WebSocketHub` stores active WebSocket connections.

When backend state changes:

1. backend calls notifier
2. notifier schedules `broadcast_state(...)`
3. every connected frontend receives:
   - `type = "state"`
   - `payload = current backend state`

This means the frontend can stay live-synchronized without polling only.


24. Frontend role
-----------------
Files:
- `frontend/index.html`
- `frontend/js/app/app.js`
- related UI modules

The frontend is mainly a viewer/controller layer.

It does not run the vision pipeline.
It does not infer moves from camera data.

Its job is:

- connect to backend WebSocket
- fetch fallback state via HTTP if needed
- render the board
- render move list
- render evaluation/top lines
- allow new game and manual move submission

So architecturally:

- vision is the observer
- backend is the authority
- frontend is the presentation layer


25. Full sequence for one real-world move
-----------------------------------------
This is the most important end-to-end explanation.

Suppose a human physically plays a move on the real board.

Step 1:
The camera captures new frames continuously.

Step 2:
`LatestFrameCamera` stores the newest frame.

Step 3:
`LiveProcessor` decides it is time to process one frame.

Step 4:
`ChessVisionTracker.process_frame()` runs.

Step 5:
The frame is warped to board view.

Step 6:
Squares are classified into empty/white/black.

Step 7:
The current occupancy observation is standardized into the internal orientation.

Step 8:
The stabilizer decides whether the new board occupancy is stable enough.

Step 9:
If stable and changed, the tracker asks:
"Which legal move explains this occupancy change?"

Step 10:
If a candidate move is found consistently enough, it is applied to the tracker-side game.

Step 11:
The accepted UCI move is sent to backend `/api/move`.

Step 12:
`BackendState.apply_uci()` applies the move to backend-side game state.

Step 13:
Backend schedules Stockfish analysis for the new position.

Step 14:
Backend emits the updated state via WebSocket.

Step 15:
Frontend receives the new state and updates board, moves, and analysis panels.


26. Why the system can work without full piece recognition
----------------------------------------------------------
A common question is:

"How can the program know the move if it only sees empty/white/black?"

The answer:

- it does not try to visually identify the exact piece type in each square
- it uses legal chess rules to explain the occupancy change

Example:

If one white piece disappeared from one square and appeared on another square,
the resolver checks:

- from the current legal position
- which legal move could produce exactly this pattern?

This is a strong simplification that works well for physical chess tracking.


27. Current practical assumptions
---------------------------------
The current system works under practical assumptions.

Important current assumptions:

1. The board is near the standard start position during init.
2. Lighting is good enough for square classification.
3. The camera is roughly above the board.
4. The real board is used in the orientation expected by the current setup:
   white side on the left, black side on the right.
5. The board remains visible and detectable.
6. The backend is reachable if live backend sync is enabled.


28. Current known limitations
-----------------------------
These are important to document clearly.

1. Orientation handling is setup-dependent.
   The current initialization succeeds reliably only for the currently assumed board orientation.

2. The visual model only predicts occupancy color classes, not exact piece types.

3. Mid-move hand occlusion can still cause errors if the stabilizer and vote logic are not enough.

4. Lighting has a strong effect on classification quality.

5. A badly synchronized tracker/backend pair can desync if reset rules are inconsistent.

6. The current system is optimized for a practical demo environment, not arbitrary unconstrained camera views.


29. Why the code has both tracker-side and backend-side game state
------------------------------------------------------------------
This may look redundant, but it serves different purposes.

Tracker-side game state:

- needed immediately for move resolution from occupancy
- tightly coupled to the vision pipeline

Backend-side game state:

- authoritative API state
- used by frontend
- used by engine analysis
- used by future robot integration

So the tracker does local decision-making, and the backend acts as the application-level source of truth.

31. Short architecture summary
------------------------------
The system is best understood as a pipeline:

Camera frame
-> board detection
-> square extraction
-> square occupancy classification
-> occupancy stabilization
-> legal move resolution
-> internal game update
-> backend synchronization
-> engine analysis
-> WebSocket state broadcast
-> frontend rendering

This means the project is not "one big AI model".
It is a layered system where:

- computer vision handles perception
- chess rules handle interpretation
- backend handles state and communication
- frontend handles presentation


32. Short explanation for documentation generation
--------------------------------------------------
If another AI needs a compact understanding, this is the shortest correct summary:

This project tracks a physical chess game from a live camera feed. The vision pipeline first detects and warps the chessboard, then classifies each square as empty, containing a white piece, or containing a black piece. These square-wise observations are stabilized over time to reduce noise. The stabilized occupancy pattern is then compared against the current legal chess position, and the system finds which legal move best explains the observed change. Once a move is accepted, it updates the internal game state and sends the move to a FastAPI backend. The backend stores the authoritative application state, runs Stockfish analysis asynchronously, and broadcasts updated state to the frontend over WebSocket. The frontend then renders the current board, move list, and engine analysis. The current implementation assumes a practical fixed-style setup, where the camera is roughly above the board and the white side is expected to appear on the left side of the camera image.
